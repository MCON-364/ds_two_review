Structure Selection

These phrases tell you which data structure to choose.

"Jobs/items should be handled in the order they arrived" · "first come, first served" · "FIFO"
→ Use a Queue (FIFO ordering)
Queue = oldest-in, oldest-out. The front of the queue is always the item that has been waiting the longest. In single-threaded code use ArrayDeque; in multi-threaded code use LinkedBlockingQueue.
// single-threaded
Queue<PrintJob> queue = new ArrayDeque<>();

// multi-threaded (also blocking)
BlockingQueue<PrintJob> queue = new LinkedBlockingQueue<>();
"Undo the most recent action" · "last in, first out" · "most recent first"
→ Use a Stack (LIFO ordering)
Stack = newest-in, first-out. In Java, model a stack with Deque and push/pop on the same end. Never use the legacy java.util.Stack class.
Deque<Action> undoStack = new ArrayDeque<>();
undoStack.push(action);          // add to top
Action last = undoStack.pop();   // remove from top
"Items arrive while earlier items are still being processed" · "producers submit, workers consume"
→ Use a BlockingQueue as the handoff point
A BlockingQueue is the standard producer-consumer handoff. Producers call offer(); workers call poll(timeout) or take(). The queue handles synchronization so you don't have to.
private final BlockingQueue<LogMessage> queue = new LinkedBlockingQueue<>();

// producer
queue.offer(message);

// worker
LogMessage msg = queue.poll(100, TimeUnit.MILLISECONDS);
"Count how many items exist per category / per level / per assignment"
→ Use a Map from key → count
A map lets you look up the count for any key in O(1). If the data is static use streams + groupingBy(counting()). If the data is being updated concurrently use ConcurrentHashMap + merge().
// static data — streams
Map<String, Long> byCategory = tickets.stream()
    .collect(Collectors.groupingBy(Ticket::category, Collectors.counting()));

// live concurrent data
ConcurrentHashMap<LogLevel, Integer> counts = new ConcurrentHashMap<>();
counts.merge(message.level(), 1, Integer::sum); // atomic
"Track a running count / total that multiple threads will update"
→ Use AtomicInteger
int++ is not atomic — a thread can be interrupted between the read and write, producing wrong counts. AtomicInteger.incrementAndGet() is a single, uninterruptible operation.
private final AtomicInteger totalProcessed = new AtomicInteger(0);

// in process():
totalProcessed.incrementAndGet();
"Track summary statistics (min, max, average, count) that multiple threads will update"
→ Wrap DoubleSummaryStatistics in an AtomicReference and update with updateAndGet
DoubleSummaryStatistics itself is not thread-safe. Wrapping it in AtomicReference lets you atomically replace the whole object using updateAndGet, which retries if another thread races with it.
private final AtomicReference<DoubleSummaryStatistics> stats =
    new AtomicReference<>(new DoubleSummaryStatistics());

stats.updateAndGet(existing -> {
    DoubleSummaryStatistics updated = new DoubleSummaryStatistics();
    updated.combine(existing);
    updated.accept(reading.value());
    return updated;
});

Threading Decisions

These phrases tell you whether to use threads at all, and which tools to use if you do.

"Multiple threads interact with it" · "must behave correctly when called from different threads"
→ Every shared field must be thread-safe
Two threads reading and writing the same plain field is a data race. You must either use concurrent classes (AtomicInteger, ConcurrentHashMap, BlockingQueue) or synchronize access. A volatile field ensures visibility but not atomicity — use it only for flags, not counters.
// flag: volatile is enough (one writer, many readers)
private volatile boolean running = false;

// counter: needs atomic (read-modify-write)
private final AtomicInteger count = new AtomicInteger(0);

// map with concurrent updates: ConcurrentHashMap
private final ConcurrentHashMap<K, V> map = new ConcurrentHashMap<>();
"Start N background workers" · "process messages in parallel"
→ Create a fixed-size thread pool with ExecutorService
An ExecutorService manages the thread lifecycle for you. You submit Runnable tasks; it decides which thread runs each one. Never create raw Thread objects when an executor is available.
executor = Executors.newFixedThreadPool(workerCount);
for (int i = 0; i < workerCount; i++) {
    executor.submit(this::workerLoop);
}
"workerCount must be positive" · "N must be greater than zero"
→ Validate and throw IllegalArgumentException immediately
Fail fast with a descriptive message. Passing 0 workers to a pool would create a pool that never does work — a silent, hard-to-debug bug.
if (workerCount <= 0)
    throw new IllegalArgumentException("workerCount must be positive");
"Workers should keep processing while work remains" · "drain any remaining work on stop"
→ Worker loop checks both the running flag and the queue
Checking only running would cause workers to exit the moment stop() is called, abandoning items still in the queue. Checking only !queue.isEmpty() would spin forever if producers keep adding items. You need both.
private void workerLoop() {
    while (running || !queue.isEmpty()) {
        try {
            LogMessage msg = queue.poll(100, TimeUnit.MILLISECONDS);
            if (msg != null) process(msg);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            break;
        }
    }
}
"The data is not changing while the report is built" · "analyze a collection that already exists"
→ No threads needed — use streams
Concurrent structures have overhead. If the data is already complete and nobody is mutating it while you read it, plain sequential stream operations are simpler, faster, and correct.
// No ExecutorService, no AtomicInteger, no ConcurrentHashMap needed
public long getLateCount() {
    return submissions.stream().filter(StudentSubmission::late).count();
}

State Safety

These phrases tell you how to protect internal state from leaking or being corrupted by callers.

"The builder must not expose its internal list" · "callers should not be able to mutate internal state"
→ Copy on the way in; return unmodifiable on the way out
If you store the original list reference, the caller can mutate the list after construction and silently corrupt your data. List.copyOf() creates a snapshot. Returning unmodifiable views prevents callers from changing what you return.
// constructor — defensive copy
this.submissions = List.copyOf(Objects.requireNonNull(submissions));

// return unmodifiable list
return submissions.stream()
    .filter(s -> s.score() < 60)
    .collect(Collectors.toUnmodifiableList());

// return unmodifiable map
return Map.copyOf(resultMap);
"getStats() must not expose mutable internal state" · "return a snapshot"
→ Create a new object and combine/copy the internal state into it
If you return the live DoubleSummaryStatistics object, a caller could call accept() on it and corrupt your statistics. Return a fresh object that is a copy of the current state.
public DoubleSummaryStatistics getStats() {
    DoubleSummaryStatistics snapshot = new DoubleSummaryStatistics();
    snapshot.combine(stats.get());
    return snapshot;
}
"A caller should not be able to change the builder's internal state by modifying the original list after construction"
→ List.copyOf() in the constructor
List.copyOf() creates a new, unmodifiable list populated with the elements at that moment. Changes to the original list afterwards have no effect on your copy.
public TicketReportBuilder(List<SupportTicket> tickets) {
    if (tickets == null) throw new IllegalArgumentException("tickets must not be null");
    this.tickets = List.copyOf(tickets);
}
"The class should not expose its internal collection directly"
→ Make the field private final; only expose it through controlled methods
If the field is accessible, callers bypass your API and can add/remove items without going through your validation logic.
// correct
private final BlockingQueue<PrintJob> queue = new LinkedBlockingQueue<>();

// wrong — never do this
public BlockingQueue<PrintJob> queue = new LinkedBlockingQueue<>();
"submit() should stop accepting work after stop() is called"
→ Guard submit() with the running flag
After shutdown, the workers are winding down. Accepting more work would add items the workers will never see.
public void submit(LogMessage message) {
    if (running) queue.offer(message);
}

Statistics & Aggregation

Choosing the right tool for the reporting question.

Requirement phrase Stream operation Return type
"How many submissions were late?" .filter(...).count() long
"Average score across all submissions" .mapToDouble(...).average().orElse(0.0) double
"How many submissions per assignment name?" .collect(groupingBy(..., counting())) Map<String, Long>
"Submissions whose score is below 60" .filter(s -> s.score() < 60).collect(toUnmodifiableList()) List<T>
"Average resolution time for resolved tickets only" .filter(resolved).mapToInt(...).average().orElse(0.0) double
"Min, max, count, sum, and average of processed values" DoubleSummaryStatistics + AtomicReference DoubleSummaryStatistics
Edge case rule: whenever a method returns a number aggregated over a potentially empty collection, you must handle the empty case — use .orElse(0.0) for OptionalDouble, or return 0 for counts. Never let a missing value crash the method.

Streams & Functional Decisions

When the problem is about analyzing a complete, static collection — not threading — these are your tools.

"Use streams to express the data processing logic. Do not use loops."
→ Every operation must be a stream pipeline: filter, map, collect, count, etc.
// filter → collect
public List<SupportTicket> getHighPriorityUnresolved() {
    return tickets.stream()
        .filter(t -> !t.resolved() && t.priority() == Priority.HIGH)
        .toList();
}

// filter → mapToInt → average
public double getAverageResolutionMinutes() {
    return tickets.stream()
        .filter(SupportTicket::resolved)
        .mapToInt(SupportTicket::minutesToResolve)
        .average()
        .orElse(0.0);
}

// groupingBy → counting
public Map<String, Long> getCountByCategory() {
    return tickets.stream()
        .collect(Collectors.collectingAndThen(
            Collectors.groupingBy(SupportTicket::category, Collectors.counting()),
            Map::copyOf));
}
"Build a report by combining all the smaller questions"
→ Implement each question as its own method; buildReport() calls them all
This is the builder pattern. Each method is independently testable and readable. buildReport() is just a constructor call that passes each result.
public SubmissionReport buildReport() {
    return new SubmissionReport(
        getLateCount(),
        getAverageScore(),
        getSubmissionsByAssignment(),
        getFailingSubmissions()
    );
}

Shutdown & Lifecycle

These phrases describe how a processor should stop cleanly.

"stop() tells the processor to stop accepting new work and waits until already-submitted work has been handled"
→ Three-step shutdown: set flag → interrupt workers → drain queue
  1. Set running = false — prevents new submissions from entering.
  2. Call executor.shutdownNow() — sends an interrupt to workers blocked on poll(timeout) or take() so they can check the flag and exit.
  3. Call awaitTermination — blocks the calling thread until all workers are done.
  4. Drain the queue — process any items that workers never picked up.
public void stop() throws InterruptedException {
    running = false;
    if (executor == null) return;
    executor.shutdownNow();                          // interrupt blocked workers
    executor.awaitTermination(1, TimeUnit.SECONDS);  // wait for them to exit
    LogMessage msg;
    while ((msg = queue.poll()) != null) {           // drain leftover messages
        process(msg);
    }
}
"blocks until all workers have finished, or timeout occurs, or the thread is interrupted"
→ That is exactly what executor.awaitTermination(timeout, unit) does
After shutdown() or shutdownNow(), call awaitTermination to block until the pool is empty, the timeout elapses, or the current thread is interrupted. You must call shutdown/shutdownNow first — awaitTermination alone does not stop the pool.
"why do we need the running flag at all? can't we just check the queue?"
→ Two purposes require a separate flag
1. Gate submissions: submit() must reject new work after stop(). The queue alone has no concept of "closed."
2. Signal workers: a worker loop checks running || !queue.isEmpty(). The flag tells workers "no more work is coming" so they can exit once the queue drains — without the flag they'd spin forever waiting for more items. 
// The flag serves two jobs:
public void submit(LogMessage message) {
    if (running) queue.offer(message);  // gate 1: reject new work after stop()
}

private void workerLoop() {
    while (running || !queue.isEmpty()) {  // gate 2: exit when stopped AND empty
        ...
    }
}

Pattern A — Static Report Builder (no threading)

Triggers: "the data is not changing" · "analyze a complete collection" · "use streams"

public class WidgetReportBuilder {
    private final List<Widget> widgets;  // defensive copy

    public WidgetReportBuilder(List<Widget> widgets) {
        this.widgets = List.copyOf(Objects.requireNonNull(widgets));
    }

    public long getXCount()           { return widgets.stream().filter(...).count(); }
    public double getAvgY()           { return widgets.stream().mapToDouble(...).average().orElse(0.0); }
    public Map<String, Long> byZ()    { return Map.copyOf(widgets.stream().collect(groupingBy(..., counting()))); }
    public List<Widget> getFiltered() { return widgets.stream().filter(...).collect(toUnmodifiableList()); }

    public WidgetReport buildReport() {
        return new WidgetReport(getXCount(), getAvgY(), byZ(), getFiltered());
    }
}

Pattern B — Concurrent Processor (threading + queue)

Triggers: "items arrive while others are still processing" · "background workers" · "multiple threads"

public class WidgetProcessor {
    private final BlockingQueue<Widget> queue    = new LinkedBlockingQueue<>();
    private final AtomicInteger totalProcessed   = new AtomicInteger(0);
    private final ConcurrentHashMap<Type, Integer> counts = new ConcurrentHashMap<>();
    private volatile boolean running = false;
    private ExecutorService executor;

    public void submit(Widget w)  { if (running) queue.offer(w); }

    public void start(int n) {
        if (n <= 0) throw new IllegalArgumentException("workerCount must be positive");
        running = true;
        executor = Executors.newFixedThreadPool(n);
        for (int i = 0; i < n; i++) executor.submit(this::workerLoop);
    }

    private void workerLoop() {
        try {
            while (running || !queue.isEmpty()) {
                Widget w = queue.poll(100, TimeUnit.MILLISECONDS);
                if (w != null) process(w);
            }
        } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

    private void process(Widget w) {
        totalProcessed.incrementAndGet();
        counts.merge(w.type(), 1, Integer::sum);
    }

    public void stop() throws InterruptedException {
        running = false;
        executor.shutdownNow();
        executor.awaitTermination(1, TimeUnit.SECONDS);
        Widget w;
        while ((w = queue.poll()) != null) process(w);
    }

    public int getTotalProcessed()          { return totalProcessed.get(); }
    public Map<Type, Integer> getCounts()   { return Map.copyOf(counts); }
}

Pattern C — FIFO Queue Wrapper (single-threaded)

Triggers: "first come, first served" · "one shared resource" · "jobs wait their turn"

public class WidgetQueue {
    private final Queue<Widget> queue = new ArrayDeque<>();  // or LinkedBlockingQueue if multithreaded

    public void submit(Widget w)              { queue.offer(w); }
    public Optional<Widget> next()            { return Optional.ofNullable(queue.poll()); }
    public Optional<Widget> peek()            { return Optional.ofNullable(queue.peek()); }
    public int size()                          { return queue.size(); }
}

Pattern D — Undo/Redo Stack

Triggers: "undo the most recent action" · "redo after undo" · "performing a new action clears redo"

public class ActionHistory {
    private final Deque<Action> undoStack = new ArrayDeque<>();
    private final Deque<Action> redoStack = new ArrayDeque<>();

    public void perform(Action a) { undoStack.push(a); redoStack.clear(); }

    public Optional<Action> undo() {
        if (undoStack.isEmpty()) return Optional.empty();
        Action a = undoStack.pop(); redoStack.push(a); return Optional.of(a);
    }

    public Optional<Action> redo() {
        if (redoStack.isEmpty()) return Optional.empty();
        Action a = redoStack.pop(); undoStack.push(a); return Optional.of(a);
    }
}
Before writing any code on the test, ask yourself these three questions:
  1. Is the data already complete, or is it arriving over time?
  2. Is more than one thread reading or writing the shared state?
  3. Do callers need to get back data — and could they misuse what I return?
Your answers map directly onto Patterns A/B/C/D and the state-safety rules above.
